# P5 design — ACP side panel in TurboWarp

Goal: the user chats with their existing coding agent (Claude Code, Codex, OpenCode — their own subscriptions)
from a panel inside TurboWarp. The agent works on the project through the same text dir + `agentwarp` CLI,
the bridge live-syncs, so the user watches scripts appear in the editor. No custom LLM loop.

## Where things run
```
TurboWarp (web or Desktop)                bridge (agentwarp serve, Node, localhost)        agent process
┌───────────────────────────┐   WS    ┌──────────────────────────────────┐ stdio ┌─────────────────────┐
│ agentwarp-client.js       │◄──────►│ sync engine (P4)                   │◄────►│ claude-agent-acp     │
│  ├ sync (P4)              │        │ ACP host: @agentclientprotocol/sdk  │ ACP  │ codex-acp            │
│  └ side panel UI (P5)     │        │  spawn agent, cwd = project dir     │      │ opencode acp         │
└───────────────────────────┘        └──────────────────────────────────┘       └─────────────────────┘
```
The panel is injected by the same client script (no TurboWarp fork needed; works on turbowarp.org and
TurboWarp Desktop via userscript.js). A Desktop fork stays an option if injection proves fragile.

## Bridge: ACP host
- `agents.json` (in `~/.config/agentwarp/` or project `.agentwarp/`): list of launchable agents
  `{id, label, command, args, env}`; defaults: Claude (`npx -y @agentclientprotocol/claude-agent-acp`),
  Codex (`npx -y @agentclientprotocol/codex-acp` — the official adapter; `@zed-industries/codex-acp` is deprecated), OpenCode (`opencode acp`, installed locally). All reuse the user's existing CLI logins. Resolve via PATH or `npx -y <pkg>`; detect availability at startup (`/acp/agents`).
- One ACP connection per agent per project; sessions: `session/new` with `cwd = project dir`; the project dir
  contains `AGENTS.md` and `CLAUDE.md` (generated by `agentwarp new/unpack`, pointing at the skill) so every
  agent knows the workflow.
- Client capabilities: we do NOT implement fs/terminal (agents use their own tools). We implement
  `session/request_permission` by forwarding to the panel (allow once / always / reject); default policy
  configurable (e.g. auto-allow edits inside the project dir and `bin/agentwarp …` commands).
- WS messages (added to the P4 protocol):
  client→server: `acp/agents`, `acp/start {agentId}`, `acp/prompt {sessionId, text, context}`,
  `acp/cancel {sessionId}`, `acp/permission {requestId, optionId}`, `acp/history {sessionId}`
  server→client: `acp/agents {list}`, `acp/session {sessionId, agentId, title?}`, `acp/update {sessionId, update}`
  (raw ACP session/update: agent_message_chunk, agent_thought_chunk, tool_call, tool_call_update, plan, …),
  `acp/permission-request {requestId, sessionId, toolCall, options}`, `acp/done {sessionId, stopReason}`,
  `acp/error {message}`.
- Session transcripts persisted to `.agentwarp/sessions/<id>.jsonl` so a reload of the editor restores the chat.

## Editor context sent with each prompt
The client attaches `context`: editing target name, its scripts file path, selected block → anchor + file:line
(via sourcemap), whether the project is running, stage size, current rev. The bridge prepends a compact block:
`[TurboWarp] editing: player (player/scripts.ts) · selected: a3 tick (player/scripts.ts:31) · rev 12`.

## Panel UI (client)
- Collapsible right-side column (doesn't cover stage or blocks; resizes the GUI's flex layout), toggle button
  in the menu bar; remembers width/open state.
- Agent picker + new chat; message list rendering markdown, streamed text, collapsible thoughts, tool calls
  (title, status spinner/check/cross, diff preview for edits), plans (checklist); permission prompt cards; stop
  button; input with Enter to send / Shift+Enter newline; Japanese IME safe (no send while composing).
- When the bridge pushes a new revision caused by the agent, highlight changed scripts briefly (glow) and,
  optionally, scroll to the first changed script of the editing target.

## Long-horizon work
The agents already handle long, recursive tasks (sub-agents, todo lists). What they need from us:
fast reliable feedback (`check`, `run --until`, lint), tests they can write and re-run (`agentwarp test`,
scenario files under `tests/`), a stage screenshot command to look at the result, and docs telling them the
loop. The panel must survive hours: reconnects, transcript persistence, permission defaults so the user isn't
asked every minute, and a visible plan/todo list.
